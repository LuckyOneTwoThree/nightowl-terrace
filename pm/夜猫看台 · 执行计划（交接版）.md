## 三、任务分解（WBS）

### P0 环境与骨架

- [ ] T1 基础设施：建 GitHub 私有仓库 `nightowl-terrace`（Description：夜猫看台 · 五大联赛观赛决策小程序——今晚哪场值得熬）；仓库采用小程序云开发标准布局 `miniprogram/`（页面与前端逻辑）＋ `cloudfunctions/`（云函数）；小程序项目初始化；云开发环境开通；云数据库建集合（fixtures / recommendations / storylines / predictions / checkins / boasts / users），字段与权限以设计方案第八节为准
- [ ] T2 应用骨架：5 页 tabBar（今日／本周／赛程／玩法／我的）、深色主题、各联赛主题色变量

### P1 数据层

- [ ] T3 数据抓取与生成（来源见设计方案第十二节，多源校对）：①球队字典 96 条——大陆通用译名（如「阿森纳」而非「阿仙奴」）、ID 三字母大写、主题色取队徽主色 hex，按 20/20/20/18/18 行数校验；②焦点对阵表初稿——德比／六强内战／宿敌对阵，供星级判据自动命中；③五大联赛全量赛程——按赛程层 schema 生成 JSON，西甲已赛轮次补录比分到 sc 字段。①②产出后由 Notion 侧验收
- [ ] T4 导入云数据库；实现启动时拉取 + `wx.Storage` 离线缓存

### P2 核心页面

- [ ] T5 今日页：今晚之选 Hero 卡、今日加餐、明日预告、故事线横滑区、无球日降级
- [ ] T6 本周页：夜猫指数预算面板（0-1 背包纯前端求解）、焦点 Top 5–8、雷区预警
- [ ] T7 赛程页：日历视图（日期主键）、轮次视图、联赛与星级筛选、tbd 标注
- [ ] T8 我的页：关注球队多选（可跳过，存本地）、主队角标与自动提级

### P3 玩法

- [ ] T9 盲评猜球：commit-reveal 封存、云函数结算（胜平负 3 分＋比分 +2、冷门翻倍）、周榜与总榜
- [ ] T10 夜猫榜：S2 及以上开球后 30 分钟内打卡、时长统计、每周战报
- [ ] T11 德比法庭：★★★ 场次赛前狂言（≤40 字）、赛后自动应验／翻车标注
- [ ] T12 盲盒开球：隐藏对阵抽签、条件限定

### P4 传播

- [ ] T14 分享卡片带参数接龙；openGid 群维度排行榜

## 四、数据资产交付方式

- **球队字典（96 条）与焦点对阵表**：执行方随 T3 一并产出（产出规范见 T3），Notion 侧验收后迁入 Notion 数据库作为 SSOT
- **种子推荐层／故事线层（揭幕周）**：由 Notion 侧产出，JSON 格式遵循设计方案第五节；看点文案与夜猫絮语是产品人格，不外包
- **全量赛程（约 1,752 条）**：执行方负责抓取，来源以设计方案第十二节列出的官方源为准，多源校对；schema 不得改动，新增字段须先改设计方案
- 后续数据维护建议迁入 Notion 数据库作为 SSOT，导出 JSON 同步云数据库

## 五、执行方须知（硬约束）

1. 动手前通读《夜猫看台 · 产品设计方案（定稿）》全文；推荐判据、玩法规则、命名体系以该文档为准。
2. 关键算法直接按方案实现：夜猫指数公式（第六节）、0-1 背包（第六节）、commit-reveal 与结算逻辑（第八节）。
3. 模块与文案命名必须使用设计方案第二节的品牌名（今晚之选、夜猫指数、夜猫榜、盲评猜球、盲盒开球、雷区预警、德比法庭、补番房、夜猫絮语）。
4. 不做实时比分与直播源；比分随每周数据更新补录 sc 字段后触发自动结算。
5. 主包体积 < 2MB；深色配色、移动端优先；默认只渲染当前周视图。
6. 任何 schema、规则、判据的改动需求，先回报，确认后改设计方案再改实现。
7. 交接方式：两份文档由 Lucky 导出为 Markdown 放入仓库 `docs/`（[design.md](http://design.md)、[execution-plan.md](http://execution-plan.md)）作为执行快照；Notion 文档为准绳，变更后重新导出同步。

## 六、风险与对策

|风险|对策|
